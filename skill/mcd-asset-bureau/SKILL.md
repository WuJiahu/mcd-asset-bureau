# 麦门资产管理局 · mcd-asset-bureau

> 一句话：**你的麦门权益不是"优惠"，是"资产"——有面值、有到期日、有衰减率、会无声蒸发。**

## 这个 skill 解决什么

普通"省钱助手"做的是 **单次订单比价**：这一单怎么买便宜。
本 skill 做的是 **跨时段的资产清算**：你手上所有麦门权益，在各自到期日的约束下，按什么顺序处置能挽回最多价值。

两者的差别是决定性的：

| 维度 | 订单比价型 | 资产清算型（本 skill） |
|---|---|---|
| 优化对象 | 单笔订单 | 全部权益的时间轴 |
| 核心变量 | 折扣力度 | **到期日 × 面值 = 日衰减率** |
| 沉默损失 | 不感知 | **计算并前置**（蒸发账单） |
| 零成本动作 | 不覆盖 | **置顶**（领券/预约抽奖等 +EV 免费机会） |
| 输出 | 推荐一个套餐 | **今日该做哪三件事，为什么是这三件** |

**铁律：任何输出都必须以"该动哪笔资产"开头，禁止以餐品列表开头。** 用户要的是调度，不是菜单。

## 第一步：采集（固定 6 个读工具，顺序不可乱）

按此顺序调用，前三个是资产本体，后三个是价值基准与机会窗口：

| # | 工具 | 取什么 | 用途 |
|---|---|---|---|
| 1 | `query-my-coupons` (pageSize=200) | 券名、用券价、有效期、时段、渠道标签 | 券资产台账 |
| 2 | `query-my-account` | availablePoint / accumulativePoint / expiredPoint / currentMouthExpirePoint | 积分资产 + 蒸发账单 |
| 3 | `query-my-prizes` (pageSize=50) | 奖品名、statusText、timeRemindText、recordTime | 奖品资产（最易被遗忘） |
| 4 | `campaign-calendar` | 未来 7–14 天活动，尤其是"预约""开抢""限时" | 零成本 +EV 窗口 |
| 5 | `mall-points-products` (catRuleIds="1>4") | 可兑换商品券及其所需积分 | 推算积分兑换率 |
| 6 | `query-nearby-stores` (searchType=2, beType=1, city, keyword) | storeCode | 后续核价/下单的锚点 |

**降级规则（重要）**：工具报"未登录/无权限"时，不要中断、不要编数据。跳过该维度并在报告中标注"该维度未采集（原因）"。宁可缺失，不可虚构。

**不要做的事**：
- 不要在这一步调 `query-meals` / `calculate-price`。它们是第二步的核价工具，此时候价没有意义、且浪费调用。
- 不要因为券多就省略 `query-my-prizes`。奖品没有"券包"入口，是蒸发率最高的一类资产。

## 第二步：估值（决定 skill 成色的地方）

MCP 只给"用券价格"，**不给原价**。所以券的面值必须自己算出来，不能拍。

### 2.1 券面值 = 不用的价格 − 用的价格

对每张有效券：
1. 从券名和用券价反推对应餐品（如"11.9元麦辣鸡腿堡" → 麦辣鸡腿堡单品）；
2. 调 `query-meals` 取该 storeCode 下该餐品原价（注意：`beType=1` 时**不传 beCode**，传了会报错）；
3. 面值 `v = 原价 − 用券价`。

**核不出来的券，面值记 `null`，标注"待核价"，并排除在合计之外。** 绝不用"估计约 15 元"这类数字充数——一个错误的估值会让整个优先级排序失真。

### 2.2 套餐券的坑

"龙焰 2 件套 ¥20.48" 这类券对应的是**套餐而非单品**，单品原价相加会高估面值。正确做法：用 `calculate-price` 对同一 `items` 分别带券/不带券算两次，取差额。若套餐不可拆分，直接标注"组合券，面值以实算为准"。

### 2.3 积分兑换率

从 `mall-points-products` 取若干可兑换商品券（如"XX 汉堡券 500 积分"），用其对应餐品原价 ÷ 所需积分，得到单积分价值（元/积分），**取中位数**作为 `unit_value`。
典型区间 0.03–0.05 元/积分。若取不到样本，`unit_value` 记 `null`，报告中积分只报数量、不折算金额。

### 2.4 奖品估值

门票/活动类奖品没有公开标价 → 记 `"非货币资产"`，不折成金额，但**必须计入待办**（闲置门票的真实成本是"占用了你的一个周末"）。

## 第三步：计算（交给脚本，不要心算）

把采集与估值结果写成 `assets.json`（schema 见 `references/ledger-schema.md`），然后：

```bash
python3 scripts/asset_ledger.py assets.json
```

脚本会输出四块：**蒸发账单 → 日衰减率排名 → 今日清算指令 → 分渠道可执行清单**。加 `--html out.html` 另出一张可视化台账卡。

脚本是纯标准库、无依赖、可离线跑；`scripts/sample_data.json` 是可直接运行的样例，可用来验证环境。

**为什么必须走脚本**：日衰减率涉及"小时级剩余时间"和边界情况（今天 23:59 到期 vs 明天 00:00 到期，θ 差一倍），心算会系统性出错，而错排优先级正是这个 skill 唯一不能犯的错。

### 核心指标定义

| 指标 | 公式 | 含义 |
|---|---|---|
| 面值 v | 见第二步 | 该资产值多少钱 |
| 剩余时长 d | (到期时刻 − 现在) / 24h，下限 1/24 | 以"天"计，含小数 |
| **日衰减率 θ** | `v / d` | **每拖一天损失多少元**，核心排序依据 |
| 年化损耗率 | `365 / d × 100%` | 制造紧迫感的直观指标 |
| 蒸发率 | `expiredPoint / accumulativePoint` | 历史体检，用于开场震撼 |
| 风险敞口 | Σv(7 天内到期) | 一周内可能蒸发的总额 |

## 第四步：输出（固定三段式，顺序不可调换）

### 第 1 段：状态陈述（1 句话，带硬数字）

以"蒸发账单"开场，不要客套。范例：

> 你累计获得 833.6 积分，**已过期 721.9（86.6%）**，按当前兑换率折合约 ¥28.9 已经无声蒸发；眼下还有 ¥XX.X 的权益在 7 天内到期。

如果没有历史过期数据，就报"当前在险敞口"，不要编造历史。

### 第 2 段：今日清算指令（3 条，不多不少）

按 **tier → θ** 双键排序，取前 3：

| Tier | 判定 | 理由 |
|---|---|---|
| T0 | 零成本、正期望的免费动作（领券、预约抽奖、预约活动） | ROI 无穷大，且**过了窗口就永久消失** |
| T1 | 24 小时内到期 | 明天归零 |
| T2 | 7 天内到期 | 本周必须安排 |
| T3 | 其余 | 有缓冲 |

每条指令必须包含四要素，缺一不可：
**动作 → 资产名 → 面值/省多少 → 截止时间（含"还有 X 小时"）**

范例：
> **① 今天 23:59 前用掉「11.9 元麦辣鸡腿堡」（面值 ¥13.1，剩 9 小时，θ=¥34.9/天）**
> ② 现在预约「10-24 00:00 积分霸王餐抽奖」—— 零成本，过点即失
> ③ 10-25 前用掉「麦旋风买一送一」（面值 ¥15，θ=¥7.5/天）

### 第 3 段：冗余与风险提示（只在有料时写）

- **重复券**：同名同价的多张券 → 提示"你有 2 张相同的 X，一单只能用一张，需拆成 2 次消费，否则第 2 张会跟着第 1 张一起到期"。
- **不可执行券**：有效期含"仅周一至周五""10:30–23:59"等限制，与用户实际可用时间冲突时，明确点出"这张券实际只剩 X 个可执行日"。
- **渠道限制**：只有"外送专用"的券在到店场景清零价值。

## 进阶：多餐次联合配置

用户说"这周要吃 N 顿，帮我排一下"时，进入配置模式：

1. 先确认 N、每顿预算区间、能否到店、是否接受外送；
2. 一单一张券是硬约束 → 这是一个 **N 个餐次 × M 张券的匹配问题**，脚本的 `--allocate N` 参数会做最大节省匹配并输出安排表；
3. 匹配后仍剩余的券，单独列为"本周无法消化"清单，并给出处置建议（转赠/放弃/拆单）。

**不要为了"用掉券"而虚构需求**：如果 N 小于券的数量，直说"这批券注定有 X 张用不完"，而不是硬凑餐次。

## 参数陷阱清单（照抄会报错）

| 场景 | 正确 | 错误 |
|---|---|---|
| 到店自取 `beType=1` | `orderType=1`，**不传 beCode** | 传了 beCode 直接报错 |
| 得来速 `beType=5` | `orderType=1`，**必传 beCode** | 漏 beCode |
| 外送 `beType=2` | `orderType=2`，**必传 beCode** | 用 storeCode 冒充 beCode |
| 团餐 `beType=6` | `orderType=2`，必传 beCode + `gmServiceCode` | 漏助餐服务码 |
| 预约单 | 所有相关调用都要带同一个 `reservationDate`（`yyyy-MM-dd HH:mm`） | 只在 create-order 带 |
| 价格单位 | 返回**分**，展示要 ÷100 | 直接当元 |
| 下单 | `takeWayCode` 取自 `calculate-price` 的 `takeWayList[].code` | 自己编 |
| 抽奖 | 必须先展示 `drawDecision.nextConsumption` 并取得明确确认 | 直接调 `draw-lottery` |

## 安全与边界

- **任何下单/支付/抽奖动作，必须先把完整明细摆给用户并取得明确"确认"，才可调用写工具。** 本 skill 默认只做只读清算，不主动下单。
- 不询问、不记录手机号、地址、身份证等个人信息；需要配送时由用户自己在麦当劳 App 内完成。
- 价格、库存、活动以官方实时返回为准；脚本算出的价值是**基于当前快照的估算**，必须在输出中声明这一点。
- 不提供医疗或营养建议；若用户问减脂，只做"在给定约束下选品"，不做健康结论。
