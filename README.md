# 麦门资产管理局 · mcd-asset-bureau

> **你的麦门权益不是"优惠"，是"资产"——有面值、有到期日、会衰减、会无声蒸发。**
>
> 别人帮你把这一单买便宜，我帮你把所有会过期的权益，在归零之前兑现。

一个基于麦当劳 MCP 的 WorkBuddy Skill。它不推荐套餐，它做**清算**。

---

## 为什么要做这个

翻了一遍本次大赛的排行榜，前 10 名里有 6 个是"省钱 / 预算 / 优惠券"方向，另外还有一堆热量计算和人格测试。

它们解决的是同一个问题：**这一单怎么买更便宜。**

但真实场景里，比"买贵了"更常见、损失更大的是另一件事——**你的券和积分，在你没注意的时候过期了。**

下面这份报告来自一个真实账号的实测快照（已脱敏，保留结构与数值，无任何个人信息）：

```
【一】蒸发账单
  累计积分 833.6｜已过期 721.9｜蒸发率 86.6%
  折合已蒸发金额：¥28.88（按 0.04 元/积分）
  ⚠ 超过一半的历史积分从未被兑现——这不是优惠问题，是调度问题。

  在险敞口（7 天内到期）：¥56.30
  可回收价值（全部未失效）：¥57.29
```

这个账号**历史上 86.6% 的积分就这么没了**，而持有人完全无感。同一份快照里还有：

- 6 张券里 **2 张当天 23:59 到期**，且是两张不同券——一单只能用一张，**当天不拆两单就必然损失 ¥13.10**
- 2 张**完全相同的 ¥20.48 券**，同一天到期，注定有一张要被浪费
- 1 个「处暑」门票奖品，中奖于 8 月 27 日，**闲置近两个月**，因为在 App 里根本看不到入口
- 活动日历里 10-24 零点有个**免费抽奖**，需要提前预约——零成本，过点即失

这些损失没有一项是"买贵了"造成的。它们全都是**调度问题**。

## 核心思路：把会员权益当成资产组合

| 权益类型 | 金融等价物 | 关键属性 |
|---|---|---|
| 优惠券 | **有到期日的看涨期权** | 行权成本 = 用券价，权利金 = 已付出的注意力 |
| 积分 | **会贬值的现金** | 有兑付率、有清零日、**已过期部分就是沉没成本** |
| 抽奖奖品 | **已实现的头寸** | 藏在二级入口，最容易忘记 |
| 活动窗口 | **零成本的免费期权** | 成本 0，期望为正，**过期后永久消失** |

于是问题从"今天吃什么"变成了一个可计算的问题：

> **在各自的到期日约束下，按什么顺序处置这些权益，能挽回最多价值？**

### 三个核心指标

| 指标 | 公式 | 作用 |
|---|---|---|
| **日衰减率 θ** | `面值 ÷ 剩余天数` | 每拖一天损失多少元，**排序的唯一依据** |
| **蒸发率** | `已过期积分 ÷ 累计积分` | 历史体检，用来开场 |
| **在险敞口** | `Σ 面值(7 天内到期)` | 一周内可能消失的总额 |

θ 是这个 skill 的核心。一张还剩 8 小时、面值 ¥19.10 的券，θ = **58.8 元/天**；一张还剩 6 天、面值 ¥15 的券，θ = 2.5 元/天。前者是后者 23 倍——但它们在任何"优惠券列表"里长得一样。

### 优先级分层

| Tier | 判定 | 理由 |
|---|---|---|
| **T0** | 零成本正期望的免费动作（领券、预约抽奖） | ROI 无穷大，且过点即永久消失 |
| **T1** | 24 小时内到期 | 明天归零 |
| **T2** | 7 天内到期 | 本周必须安排 |
| **T3** | 有缓冲 | 可排队 |
| **T4** | 有效期未知 | 先确认，别猜 |

排序规则是 **tier 为主键、θ 为次键**。不按金额排，因为金额大的不一定最急；也不按到期日排，因为明天到期但只值 1 元的券不值得占用今天的一顿饭。

## 它输出什么

固定三段式，顺序不可调换：

**第 1 段 · 状态陈述**：一句话带硬数字，先说蒸发了多少。

**第 2 段 · 今日清算指令**：3 条，每条必含「动作 → 资产 → 面值 → 截止时间 → 还有多久」。

**第 3 段 · 冗余与风险**：重复券、同日到期冲突、渠道限制、面值待核价。

真实输出（节选）：

```
【三】今日清算指令
  1. [T0 零成本窗口] 立即预约抽奖：麦金喜抽积分霸王餐
     截止 10-24 23:59｜剩余 1.3 天｜成本 0，纯正期望
  2. [T1 24h内到期] 安排消费：19.9元王牌炸鸡任选2
     截止 10-23 23:59｜剩余 7.8 小时｜面值 ¥19.10｜θ 58.8 元/天
     渠道：到店、外送｜时段 10:30-23:59
  3. [T1 24h内到期] 安排消费：11.9元麦辣鸡腿堡
     截止 10-23 23:59｜剩余 7.8 小时｜面值 ¥13.10｜θ 40.3 元/天

【四】冗余与风险
  · 重复券「1024"码"力翻倍」×2 张，一单仅可用一张，需拆 2 次消费
  · 同日到期冲突 10-23：2 张券同日失效（11.9元麦辣鸡腿堡、19.9元王牌炸鸡任选2）
    一单只能用一张 → 需当天拆 2 单才能全部兑现；否则必然损失 ¥13.10
```

注意第 2 条：**它不是"最省钱的方案"，而是"最该现在动手的资产"**。这是本 skill 与省钱类工具最根本的区别。

## 安装

### 1. 配置麦当劳 MCP

配置文件见 [`mcp-config.example.json`](mcp-config.example.json)，把 `${MCD_MCP_TOKEN}` 替换为你的实际 Token：

```json
{
  "mcpServers": {
    "mcd-mcp": {
      "type": "streamablehttp",
      "url": "https://mcp.mcd.cn",
      "headers": {
        "Authorization": "Bearer ${MCD_MCP_TOKEN}"
      }
    }
  }
}
```

WorkBuddy 侧边栏 →【专家·技能·连接器】→【连接器】→ 右上角【自定义连接器】→【配置 MCP】，粘贴上述 JSON 并保存，然后启用连接器。

Token 从 [麦当劳 MCP 控制台](https://mcp.mcd.cn) 申请。保存后启用连接器。

> 仓库内不含任何 Token。配置文件只使用 `${MCD_MCP_TOKEN}` 环境变量占位符。

### 2. 安装 skill

```bash
git clone <this-repo>
cp -r skill/mcd-asset-bureau ~/.workbuddy/skills/
```

### 3. 验证清算引擎

无需 MCP 也能跑，用内置的真实快照：

```bash
cd ~/.workbuddy/skills/mcd-asset-bureau/scripts
python3 asset_ledger.py sample_data.json --allocate 3 --html ledger.html
```

纯标准库，无第三方依赖，Python 3.9+ 可运行。

## 使用

配置好之后，直接用自然语言：

| 你说 | 它做 |
|---|---|
| 「清算一下我的麦门资产」 | 跑完整流程，出蒸发账单 + 今日 3 条指令 |
| 「我有什么快到期的」 | 只跑 T0/T1/T2，聚焦紧急项 |
| 「这周要吃 3 顿，帮我排一下」 | 进入配置模式，做券 × 餐次最优匹配 |
| 「我的券和积分值多少钱」 | 只做估值：面值合计、在险敞口、可回收价值 |
| 「帮我把券都用掉」 | 先算能不能用完；用不完就直说，不硬凑餐次 |

也可以只问一句：「我的麦辣鸡腿堡券还能用吗」——它会核门店、核渠道、核时段，而不是只看券包。

## 技术实现

```
mcd-asset-bureau/
├── README.md                       # 本文件
├── CONTEST_DECLARATION.md          # 参赛声明（官方模板，未改动）
├── MCP_INTEGRATION.md              # MCP Server / Tool / 调用流程 / 业务价值
├── mcp-config.example.json         # 脱敏 MCP 配置（环境变量占位符）
├── workbuddy.md                    # WorkBuddy 开发对话上下文
├── demo-ledger.html                # 渲染后的台账示例
└── skill/mcd-asset-bureau/
    ├── SKILL.md                    # 工作流、估值规则、参数陷阱、输出模板
    ├── references/
    │   ├── ledger-schema.md        # assets.json 数据契约
    │   └── mcp-field-map.md        # 实测响应结构与字段映射
    └── scripts/
        ├── asset_ledger.py         # 清算引擎（纯标准库）
        └── sample_data.json        # 真实快照，可直接运行
```

三个设计决策值得说明：

**1. 所有时间以快照的 `as_of` 为基准**
不读系统时钟。这样任何一次清算都能复算、能对账、能回放。金融系统的老规矩：可复现比"实时"更重要。

**2. 面值必须实算，不能估**
MCP 只返回"用券价"，不返回原价。所以脚本要求：`面值 = 原价 − 用券价`，其中原价来自 `query-meals` 或 `calculate-price` 双算。
**核不出来的券，面值记 `null` 并标注"待核价"，排除在合计之外。** 绝不写"估计约 15 元"——一个错误估值会让整个排序失真，而排错优先级是这个 skill 唯一不能犯的错。

**3. 用位掩码 DP 做券-餐次匹配**
"N 顿饭用 M 张券"不是贪心问题：券有星期限制和时段限制，不同餐次的可用券集不同。M ≤ 16 时用 `O(2^M · N)` 的精确 DP，超出退化为贪心。一单一张券是硬约束。

开发过程中脚本抓出过一个真实 bug：`datetime.replace(day=1)` 会保留时分秒，导致"月末"被算成"次月 1 日 16:10"，θ 全盘偏移。这类边界正是**不能心算、必须落代码**的原因。

## 目标用户

| 人群 | 痛点 |
|---|---|
| **券包常年 30+ 张的重度用户** | 根本不知道哪张快过期 |
| **囤券型消费者** | 看到就领，领完就忘，蒸发率通常超过 50% |
| **团队里的"点单担当"** | 一群人吃饭，要在预算、口味、券之间做约束求解 |
| **把会员体系当游戏玩的人** | 想要的不只是省钱，而是"我的资产配置是否最优" |

## 局限与边界（请认真读）

- **面值是基于快照的估算**，价格、库存、活动以麦当劳官方实时结果为准。
- **积分兑换率 `unit_value` 是推算值**（取积分商城可兑换商品的单积分价值中位数）。取不到样本时脚本只报数量、不折金额。
- **奖品不折算金额**：门票类非货币资产，估值会引入虚假精度，宁可只列待办。
- **不主动下单、不主动抽奖**。所有写操作必须先把明细摆出来、取得用户明确确认。默认只做只读清算。
- **不接受、不记录**手机号、地址等个人信息；需要配送时请在麦当劳 App 内完成。
- 不构成医疗、营养或投资建议。
